Architecture

Four layers, each calling only the one below

Your application talks in rectangles and text. Each layer below turns that into something simpler, until the bottom layer is just writes to hardware registers.

Start-up, in detail

Everything that happens before main()

From the moment the chip comes out of reset to the first line of main.c takes a few milliseconds, most of it spent waiting for the crystal. Every address, value and instruction below is taken from the current Debug build (build/Debug/lcd.elf).

  1. ResetHSI 8 MHz
  2. Boot pinsflash at 0x0
  3. Vector fetchSP, PC by hardware
  4. Reset_Handlersets SP
  5. SystemInit8 → 48 MHz
  6. Copy .data4 B
  7. Zero .bss440 B
  8. C library init2 functions
  9. main()0x0800 0290
1

Something resets the chip

A reset can come from the supply rising at power-on, the RESET button pulling the NRST pin low, software (the core's SYSRESETREQ bit, the usual way a debugger resets the chip), or a watchdog. Each sets a flag in RCC_CSR, which stays set until firmware clears it, so you can always ask afterwards why the chip restarted.

Every register then takes its reset value from the reference manual (RM0008). This is the state the start-up code has to work from:

2

The boot pins decide what appears at address 0

The Cortex-M3 always starts by reading address 0x0000 0000. The STM32 samples its BOOT0 and BOOT1 pins on the 4th clock edge after reset and maps (aliases) one of three memories there. The memory stays reachable at its own address too.

BOOT1 (PB2)BOOT0Mapped at 0x0000 0000Use
x0Main flash, 0x0800 0000Normal: runs your program. The Blue Pill's BOOT0 jumper sits on 0.
01System memory, 0x1FFF F000ST's built-in serial bootloader (UART1). Also a rescue mode when your firmware blocks SWD.
11SRAM, 0x2000 0000Running code loaded into RAM by a debugger.
3

The core reads two words: no code has run yet

The hardware itself loads the stack pointer from the first word and the program counter from the second. Bit 0 of the reset address is 1: on Cortex-M that bit means "Thumb code" (the only instruction set it has), and it is dropped when the address goes into PC. From here on the core runs from the real flash address 0x0800 xxxx, not the alias.

0x0000 0000 → SP0x2000 5000_estack: one byte past the end of the 20 KB RAM. The stack grows down from here.
0x0000 0004 → PC0x0800 0299Address of Reset_Handler (0x0800 0298) + 1 for Thumb.

Those two words are the start of the vector table (g_pfnVectors in startup_stm32f103xx.S): 76 addresses, 304 bytes, that the core uses whenever an exception or interrupt happens. The linker script places it first in flash with KEEP(*(.isr_vector)), so it is never discarded even though no code calls it.

How one handler gets a real function and the others don't: the startup file declares every handler as a weak alias of Default_Handler. A normal definition anywhere else wins over a weak one, so timebase.c's SysTick_Handler replaces it. Every handler you don't write lands in an endless loop, which is why an unexpected interrupt or a HardFault looks like a hang.

/* startup_stm32f103xx.S */
  .weak      SysTick_Handler
  .thumb_set SysTick_Handler, Default_Handler

Default_Handler:
Infinite_Loop:
  b Infinite_Loop                 @ 0x0800 02E8: branch to itself, forever

ST's file lists every interrupt of the STM32F103 family up to TIM7 (IRQ 59), including peripherals the C8 doesn't have (TIM8, FSMC, SDIO). Unused entries cost 4 bytes each and do no harm.

Note the order: SystemInit runs before the copy and zero loops. It speeds up everything after it, but it also means it cannot use global variables (next stage).

5

SystemInit() takes the clock from 8 to 48 MHz

Written in C in Src/clock.c and called from assembly. Each step is one or two register accesses:

WhatRegister writeWhy
aPoint VTOR at the vector tableSCB_VTOR = 0x0800 0000Exceptions read the table at its real flash address instead of through the boot alias.
b1 flash wait state + prefetchFLASH_ACR = 0x0000 0011Flash can't answer in one cycle above 24 MHz. This must be set before the clock goes up, or the CPU reads wrong instructions.
cStart the 8 MHz crystalRCC_CR |= HSEON (bit 16)
wait for HSERDY (bit 17)		The crystal needs about 2 ms to oscillate steadily. The wait gives up after 200,000 loop passes (50–100 ms at 8 MHz).
dConfigure PLL and bus dividersRCC_CFGR = 0x0011 0400PLLSRC = HSE (bit 16), PLLMUL = ×6 (bits 21:18 = 0100), APB1 ÷ 2 (bits 10:8 = 100, max 36 MHz), AHB and APB2 ÷ 1. SW is still HSI, so the clock doesn't change yet.
eStart the PLLRCC_CR |= PLLON (bit 24)
wait for PLLRDY (bit 25)		The PLL locks onto 8 MHz × 6 = 48 MHz.
fSwitch SYSCLK to the PLLRCC_CFGR |= SW_PLL
wait until SWS reads PLL		Register now reads 0x0011 040A. From the next instruction the core runs 6× faster.

If the crystal never starts

Step c times out, HSEON is cleared and the PLL takes the internal oscillator instead: HSI ÷ 2 × 12 = 48 MHz. Same frequency, so SPI speed and the 1 ms tick are unchanged, only less accurate (the internal oscillator is about ±1 %). clock_uses_crystal() tells you which one you got.

Why it uses no global variables

It runs before stage 6, so any global would read random RAM, and anything it wrote would be overwritten by the copy and zero loops a moment later. It only uses registers and its own stack. If the PLL fails to lock it returns early and the chip stays on 8 MHz, making every timing 6× slow.

6

Globals get their starting values: .data and .bss

The compiler sorts every global and static variable into a section, and the linker script decides where each section goes. Variables with a starting value need two places: their value is stored in flash (it survives power-off), and the variable itself lives in RAM (it can change). The copy loop moves the values across. Variables without a starting value must be 0 by the C standard, so the second loop simply clears them.

In C 
static uint32_t count = 5;      // .data   : 5 in flash, copied to RAM
static uint32_t s_ticks_ms;     // .bss    : cleared to 0
static const uint16_t lut[] =   // .rodata : stays in flash, no copy,
    { 0x0000, 0xFFFF };           //           no RAM used
void f(void) { int x; }        // stack   : not touched at start-up
In stm32f103x8_flash.ld (simplified) 
_sidata = LOADADDR(.data);
.data : { _sdata = .; *(.data*) ; _edata = .; }
        >RAM AT> FLASH   /* lives in RAM, stored in flash */
.bss  : { _sbss = .;  *(.bss*) *(COMMON); _ebss = .; }

7

The C library initialises itself: __libc_init_array

A newlib function at 0x0800 0170. It calls every function listed in the .preinit_array and .init_array sections, plus an empty _init. In C++ this is where global constructors run; in this C project it calls two library helpers and nothing of yours:

.init_array entryFunctionWhat it does
0x0800 01C9register_finiRegisters the library's clean-up code with atexit. That registration is why the 400-byte atexit table sits in .bss.
0x0800 0155frame_dummyRegisters exception-unwinding tables if there are any. Here there are none, so it returns.

A C function marked __attribute__((constructor)) would be added to this list and run here, before main().

8

main() is called, and must never return

bl main at 0x0800 02CA jumps to 0x0800 0290. An embedded program has nowhere to return to: if main() ever returned, Reset_Handler would fall into LoopForever and the clean-up functions in .fini_array would never run. That is why main.c ends in for (;;).

Already done when main() starts

  • Core at 48 MHz, APB1 24 MHz, APB2 48 MHz
  • Flash at 1 wait state with prefetch
  • VTOR at 0x0800 0000
  • Stack pointer at 0x2000 5000
  • Every global holds its starting value or 0

Still your job

  • SysTick is off. Call timebase_init() first, or millis() stays 0 and delay_ms() waits forever.
  • Every peripheral clock is off: enable GPIOA, GPIOB, SPI1, TIM3 in RCC before touching them.
  • The LCD pins are floating inputs until configured.
  • No interrupt is enabled in the NVIC.

The STM32F103C8T6 as it really is: a 48-pin LQFP package, pin 1 at the dot, numbered counter-clockwise. Inside it, the peripheral that drives each pin. Outside, the wires to the TFT module and the ST-Link. Hover or tap any wire, pin or signal name to follow it end to end.

Build and flash

From source to the chip

./flash.sh does all four steps. OpenOCD can do the last one instead, from openocd.py or a terminal.

Configure

CMake

Reads CMakeLists.txt and cmake/*.cmake, writes a Ninja build.

cmake --preset Debug
Compile + link

arm-none-eabi-gcc

C11, -Wall -Wextra -Wpedantic, Cortex-M3 Thumb. The linker script places sections; unused functions are dropped.

cmake --build --preset Debug
Output

lcd.elf → lcd.bin

The ELF keeps symbols and line numbers for debugging; the BIN is the raw bytes for flash.

arm-none-eabi-objcopy -O binary
Program

ST-Link over SWD

Writes flash from 0x0800 0000 and resets the chip. Only one program can use the ST-Link at a time.

st-flash --reset write lcd.bin 0x08000000
Where to start

Reading order and your first steps

Suggested reading order

  1. board.h: pins and clocks, the vocabulary of everything else.
  2. spi.c: how one byte leaves the chip (TXE, BSY, DFF).
  3. st7789.c: the init sequence and the window / pixel model.
  4. gfx.c: how text becomes pixels.
  5. clock.c and startup_stm32f103xx.S: what happened before main().

Keep RM0008 (STM32F1 reference manual) and the ST7789V datasheet open; the comments cite their section names.

Rules the code follows

  1. Every register access goes through a name in stm32f103_regs.h.
  2. Every wait loop has a timeout; functions return 0 on success, -1 on error.
  3. A peripheral needs its clock enabled in RCC before its registers respond.
  4. The build must stay free of warnings.
  5. New source files go into CMakeLists.txt, never into the managed cmake/ files.

When the screen stays blank, openocd.py shows each LCD register decoded while the program runs.
